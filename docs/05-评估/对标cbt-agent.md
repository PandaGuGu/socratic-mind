# 对标 cbt-agent

对象：[lcy05/cbt-agent](https://github.com/lcy05/cbt-agent)（v0.1.0，MIT）。它的 README 自述"最小介入的认知行为自助练习闭环"，10 阶段图 + 严格 JSON。

本文只回答一件事：**它做对的地方，我们是否对上了；哪些是我们多出来的；哪一条还没对上。**

| # | 机制 | cbt-agent 的做法 | 我们的做法 | 结论 |
|-|-|-|-|-|
| 1 | 流程即图 | Spring AI Alibaba Graph，10 个阶段 | `FlowDefinition` + `CbtFlow.advance`，8 核心 + 3 可选（行为实验 / 问题解决 / 判断） | **对齐，且可编辑** |
| 2 | 安全门是硬入口 | 每轮先过 `safety_triage`，CBT 节点结构性不可达 | `SafetyScreener` 在 `handle()` 最前，命中即转 `SAFETY_HOLD`；画布不提供指向 CBT 的安全边 | 对齐 |
| 3 | 模型只提建议 | 输出严格 JSON，枚举白名单校验后才由代码决定路由 | 话术由脚本给，模型只参与"平衡想法 / 总结"两处；路由由关键词与分支规则决定 | **路线不同**：我们的模型面更小，所以不需要 JSON 路由；若将来让模型出题，必须补枚举校验 |
| 4 | 输出校验 | `NodeOutputGuard`：JSON 解析 + 枚举 + 1 次重试 + `parse_error` 兜底 | `GuardedChatPort`：长度 / 禁句 / 与输入重合度 + **带原因重写** + 模板兜底；`guardRule` 落进轨迹 | 对齐（校验维度不同，我们多了重合度与审计） |
| 5 | 保存必须显式授权 | `recordApproved` 只能由用户请求写入，模型改不了 | 只有 `POST /{id}/confirm` 能写 `userConfirmedThought`；房间的确认条只在该状态下出现 | 对齐 |
| 6 | 持久化 | `MysqlSaver` 管 checkpoint，业务表独立，重启不丢 | `cbt_session` / `cbt_message` / `cbt_turn` 三表 + `JdbcCbtSessionStore`；H2 文件库实测重启存活，PG 配置已就位 | 对齐（PG 实跑待网络） |
| 7 | 前端轨道 | 思维链轨道 + 分支标记 + 保存决策条；只能看到最后停在哪个节点 | `/internal` 轨道五态 + 分支 + 字段快照 + 策略拦截标签；`/room` 房间前台 | 对齐并超出（有完整轨迹） |
| 8 | 完整轨迹 | **`GET /trace` 尚未实现**（README 已知边界） | `CbtTurnEvent` 逐轮事件：动作、阶段迁移、安全规则、模型来源、拦截规则、耗时 | **超出** |
| 9 | 提示词资产 | 11 份，哈希锁定 | `prompts/cbt/*.md` + `PromptAssetTest` 锁结构（锚点、占位符、无 CRLF） | 对齐（我们锁结构不锁哈希，改文不必改哈希） |
| 10 | 测试 | 21 项离线：16 项图行为验收（V1–V12、A1–A4）+ 5 项提示词 | 63 项：轨迹 7、守卫 9、策略存储 5、装饰器 5、发布校验 7、画布 3、分支 4、提示词 4 + 既有链路 19 | 数量超出；**用例编号体系不如他们清晰** |
| 11 | 诚实边界 | README 明确"无认证、无会话列表、只适合本机" | 后台三处徽章（内存档 / 桩模型 / 无鉴权）+ 文档 §10.6、§11.6 | 对齐 |
| 12 | 可运营性 | 无（改流程要改代码） | 画布改话术/去向/分支/判断节点，策略页改禁句与阈值，均热加载 | **超出** |

## 结论

- **对齐 10 条**，其中 2 条走的是不同实现（校验维度、模型参与面）；
- **超出 3 条**：完整轨迹、可运营的画布与策略、审计；
- **未对齐 0 条**。持久化已补上（H2 端到端验证，PostgreSQL 配置同源、待网络条件实跑）。

## 已补的差距：落库

cbt-agent 用 `MysqlSaver` 管 checkpoint、业务表单独存；我们的对应物已落地（[数据模型与DDL](../02-设计/数据模型与DDL.md) §2.1）：

| 表 | 对应现在内存里的什么 |
|-|-|
| `cbt_session` | `CbtSession` 的字段（stage、targetProblem、candidateThought、userConfirmedThought、summary…） |
| `cbt_message` | `history()`，含 role / stage / at |
| `cbt_turn` | `trace()`，一条 `CbtTurnEvent` 一行 |

只补 checkpoint 不补业务表，会出现"能续跑但查不到当时说了什么"，这正是 cbt-agent 把两者分开的原因。

## 可借但不急

1. **图行为验收的编号用例**（V1–V12、A1–A4）：他们用固定编号盯回归，读起来比我们"按类分散"的测试清楚。可以照着把我们的 63 项重命名分组，不改变覆盖。
2. **严格 JSON + 枚举白名单**：等哪天让模型生成问题或决定路由，这套是前提。现在不用，是因为问题文本来自脚本。
3. **`recordApproved` 的命名**：他们的名字直接说明"这是授权动作"，比我们的 `confirm` 更不容易被误用。

## 不要借的

- 单端点 `/turn`：它把"发消息 / 确认 / 结束"压成一个入参，安全但不好扩展；我们的分端点 + `awaitingUser` 状态更清楚。
- 哈希锁定提示词：每次合理改写都要动哈希，他们用 CI 兜住了，我们暂时没这个必要。
