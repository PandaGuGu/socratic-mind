# 文档规范

适用于 `docs/` 下所有文件。

## 1. 文件头必须有序言块

```yaml
---
title: 第 N 章 标题
status: 定稿        # 定稿 | 草案 | 待决策 | 归档
updated: YYYY-MM-DD
---
```

`status` 不是装饰。`草案` 的章节不能被当成开发依据引用。

## 2. 编号

- 章：`第 N 章`，与文件名前缀 `NN-` 一致，**一一对应，不许跳号**。
- 节：`N.M`；子节：`N.M.K`；引用写 `§N.M`。
- 章号一经发布不再重排。新内容用 `03-a-xxx.md` 挂靠，避免外部链接失效。
- 表、图不单独编号（第一版规模不需要）；需要被引用时，用"§N.M 的那张表"描述。

## 3. 交叉引用

| 场景 | 写法 |
|-|-|
| 其它章 | `[第 5 章](../01-方案/05-双Graph设计.md)` |
| 跨目录 | `[§4.2](../01-方案/04-RAG知识数据架构.md)` |
| 同章小节 | `§5.3` |

禁止"上一章""前面提到过""如上所述"——文档会被单独转发，这些词在单章里没有指向。

## 4. 表格

- 一张表只回答一个问题。
- 对比类表格必须有"本方案"或"结论"一列，否则读者不知道为什么列这张表。
- 单元格里不写长段落；超过两句就改成小节。

## 5. 图

- 优先 mermaid 写在正文内（GitHub / VS Code / 多数 Markdown 预览都支持），保证可 diff。
- 只有截图、外部导出件、二进制素材进 `docs/assets/`，文件名用英文短横线。
- 架构图与流程图必须与正文表格一致；改图要同步改表。

## 6. 语言

- 中文正文，术语首次出现给出英文原词（如"证据单元（evidence）"）。
- 不写"我们"以外的第一人称；不用营销词（"革命性""颠覆"）。
- 结论句放段首，理由跟在后面。评审读的是第一句。

## 7. 变更

| 改动 | 必做 |
|-|-|
| 改结论 | 新增或更新 ADR，并在本章"对应的决策"表里挂链接 |
| 改数字（延迟、指标阈值） | 注明来源与测量条件 |
| 新增章节 | 更新 `docs/README.md` 索引与 `README.md` 的阅读路径 |
| 删除内容 | 不要直接删；标 `status: 归档` 并写明被谁取代 |

## 8. 目录归属

| 内容 | 放哪 | 不放哪 |
|-|-|-|
| 当前状态：每版改了什么、还差什么 | `05-评估/版本记录.md` | 不散在设计文档里 |
| 过程记录：某天的走查、联调、排障 | `99-归档/` | 不进 01–04，读者会被时间线带偏 |
| 过时的方案与说明 | `99-归档/`，并在归档索引加一行 | 不直接删，链接会断 |
| 截图 | `docs/assets/<主题>/`，文件名英文短横线 | 不放根目录，不放中文名 |

一条经验：**文档只写"现在是什么"，过程留给提交记录。** 需要解释"为什么变成现在这样"时，写 ADR，而不是给设计文档追加一段"2026-11-19 又改了"。若某篇文档的结论已不成立，把它移进归档并更新索引，别让两份互相矛盾的真值同时存在。
