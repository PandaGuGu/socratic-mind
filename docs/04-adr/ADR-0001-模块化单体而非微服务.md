# ADR-0001：采用模块化单体，不拆微服务

- **状态**：已接受
- **日期**：2026-11-17
- **相关**：[模块与技术栈](../02-架构/01-模块与技术栈.md)

## 背景

系统包含用户、会话、知识库、RAG、两个 Graph、评估六类能力。直觉上"拆微服务更专业"，但当前处于第一版，团队规模小，且业务边界仍在变动（CBT 节点尚未实现过一轮）。

## 决策

采用 **Maven 多模块的模块化单体**：一个进程、一个数据库、按包划清边界。模块间的依赖方向单向向下，`rag` 不反向依赖 `agent`。

## 备选方案与被否原因

| 方案 | 为什么没选 |
|-|-|
| 微服务（RAG / Agent / 知识库各自独立部署） | 边界未验证就拆，等于把错误固化；跨服务事务让"消息落库 + 状态推进"必须做成最终一致，而无收益 |
| 单体大泥球（不划模块） | 后续想外迁时没有缝合线；RAG 与 Graph 会互相渗透 |
| Serverless / 函数拆分 | 与长连接 SSE、Graph 有状态恢复相冲突 |

## 后果

**好处：** 本地事务即可保证会话与消息一致；调试单进程；部署一份 compose 起步。

**代价：** 单点扩展，重检索会拖慢对话；模块边界靠约定与代码评审维持，工具不会强迫。

**复查触发条件：** 出现下列任一情况，讨论拆分 `psych-rag` 为独立服务——检索 P95 影响对话首 token 超过 300ms；单个模块的发布节奏与其它模块冲突到无法同版本发布；团队超过 6 人并行开发同一模块。

## 备注

拆分时优先外迁 `psych-rag`，因为它已经是接口化调用、无业务状态，迁移成本最低。
