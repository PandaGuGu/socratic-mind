# ADR-0010 组织域与操作者身份

## 背景

v0.5.0 之前，"内部人"是一把共享令牌（`X-Internal-Token`）。它能证明"你来自内部"，
证明不了"你是谁"。于是审签页的审核人是一个输入框——谁都能填"李医生"。

同时暴露了三个会在多实例部署时立刻发作的假设：

1. 审核记录写 JSON 文件：每个副本各写一份，签字随负载均衡漂到不同机器；
2. ACL 是自由字符串：写错一个 team id，结果是"谁都看不见"或"谁都看得见"，且不报错；
3. 限流是进程内的：扩到两台机器，配额直接翻倍。

## 决策

**引入组织域：租户 → 团队 → 成员，全部落库。**

| 对象 | 作用 | 关键约束 |
|-|-|-|
| `org_tenant` | 数据边界 | 成员与文档只属于一个租户 |
| `org_team` | 可见范围的单位 | ACL 只能引用本租户的团队 id |
| `org_member` | 签字的责任主体 | 只存令牌 SHA-256；吊销写 `revoked_at`，不删行 |

四件事随之改变：

1. **两把钥匙**。系统令牌证明来源，操作者令牌（`X-Operator-Token`）证明身份。
   组织模式打开后，写操作没有操作者令牌直接 401；只有只读角色写操作 403。
2. **署名来自令牌**。审核记录的 `operator_id` / `operator_name` 由令牌解析，
   请求体里的 `reviewer` 在组织模式下被忽略。
3. **ACL 变成引用**。`acl_scope` 里的每一项必须是 `tenant:<id>` 或 `team:<id>`，
   写之前校验存在性与归属。物理上仍是文本列——换来零迁移，语义上已经不是自由字符串。
4. **状态全部可落库**。审核记录、评测留痕、限流计数各有 JDBC 实现，H2 与 PostgreSQL 共用一份 DDL。

## 后果

**变好的**：

- "谁签的字"在事后站得住：令牌 → 成员 → 姓名，链路可查；
- 跨租户泄露有了硬拦截：ACL 校验 + 检索前过滤，两道；
- 多实例不再需要粘性会话：身份、权限、计数都不在进程里。

**变差的与接受的**：

- 每次内部请求多一次成员查询（按 `token_hash` 唯一索引）；量大时要加短 TTL 缓存，
  不能退回"不查"；
- 限流走固定窗口，窗口边界可能瞬时放行 2 倍配额。要精确滑动得存时间戳，
  那是 Redis 的活；这里给的是没有额外中间件时的退路；
- 一个成员只属一个团队。多团队归属要改的是"可见范围求并集"的规则，
  比改表结构更值得先想清楚；
- 组织模式默认关闭（`psych.org.enabled=false`），单机开发不受影响。
  **上线必须打开**，否则署名仍然可自报。

## 备选方案

- **接外部 IdP（OIDC/LDAP）**：更接近企业部署，但本地开发需要 mock 身份提供方，
  且 scope 的语义要跟着 claims 走。等真有内网集成需求时再换，接口层已经隔离。
- **ACL 存 join 表**：更规范，但要迁移已有 `acl_scope` 数据，且内存档与 PG 档要各写一套。
  当前用"id 引用 + 文本列"取得同样的语义，代价是读的时候要解析。

## 补充（v0.7.1）：后台登录

上面的决策留下一个明显缺口：**只有令牌门禁，没有登录**。后果是"署名来自令牌"这件事
在浏览器里站不住——令牌存在 localStorage，谁拿到都能用，而且没有过期与登出。

补上的五件事：

| 项 | 做法 | 关键取舍 |
|-|-|-|
| 口令 | 复用前台 `PasswordHasher`（PBKDF2-SHA256，迭代次数写进字符串） | 后台额外禁止纯数字口令：能改生产配置的账号值得更严一档。本机演示档可用 `psych.security.relaxed-operator-password=true` 放宽到"≥6 位、允许纯数字"，默认关闭 |
| 会话 | `org_session` 表，`sm_sid` 走 HttpOnly + SameSite=Lax | 落库不签名：登出必须立刻生效，签名 cookie 只能等过期 |
| 失效 | `session_epoch` +1；改口令时同时撤销全部会话 | 改口令的定义之一就是"其他设备下线" |
| CSRF | 双提交：`sm_csrf` 故意可被脚本读，写请求带 `X-CSRF-Token` | 只对 cookie 认证校验；令牌认证的请求不存在被借用身份的问题 |
| 留痕 | `org_login_attempt`，成功与失败都记；失败按账号限流 5 次/分钟 | 只记失败的话，出事时回答不了"最后一次正常登录是什么时候" |

两条通路的优先级：cookie 会话 → 操作者令牌 → 都没有则拒绝。
读写不同权：**写必须有身份，读可以用系统令牌**——查登录日志不该要求你先能登录，
那是登录坏掉时唯一需要看的东西。

仍然没有的：操作者自助注册、忘记口令自助重置（需要管理员介入）、会话滑动续期。

## 职责分离（v0.7 补）

v0.6 之前只有一种能干的身份：播种脚本建一个 `admin`，所有事都由它做——审核签字和管理成员
用的是同一把钥匙，出了问题也分不清是谁的职责。v0.7 把"位置"和"能签什么字"分开：

| 职责 | 能做什么 | 不能做什么 |
|-|-|-|
| `admin` 管理员 | 成员与口令；会话原文、轨迹、导出；其余全部（破窗） | ——（代签会在审核记录里留下管理员名字） |
| `operator` 运营 | 知识入库、文档可见范围、**流程画布、输出策略、话术、安全规则、运行参数**、词库、模型配置、评测；会话**列表**（不含原文） | 知识发布/退回、安全提示确认、读会话原文 |
| `reviewer` 审核 | 知识发布/退回、安全提示确认；**已进入安全流程的会话原文** | 入资料、改文档可见范围、**改任何配置**（流程/策略/话术/规则/参数/模型）、管成员、读普通会话原文 |
| `viewer` 只读 | 查看（会话列表也不含原文） | 一切写操作 |

「配置」和「审核」是两件事，混在一起是这套权限最容易出错的地方：

- **配置**（流程、输出策略、话术、安全规则、运行参数、模型、词库）全部归运营——决定"系统怎么跑、系统怎么说"；
- **审核**只回答"这份资料能不能被引用、这条提示能不能这么说"——决定"这句话能不能用"，不写系统配置；
- 回滚同样归运营：只在保存那侧做校验、回滚那侧不校验，等于留了一条绕过路径。

数据可见性单独拿出来说，因为它比"能不能改"更容易被忽略：

- 会话**列表**只回答"有哪些会话"（谁、第几步、是否安全暂停），`targetProblem` 对没有原文权限的人置空；
- 会话**原文/轨迹/原始 JSON/导出**默认只给管理员。这个产品的承诺是"不写业务状态、不替用户判断"，
  后台能随手翻所有人的原话，承诺就不成立；
- 唯一的例外是审核者：对 `SAFETY_HOLD` / `hold` / `review` / `watch` 的会话，他可以查看原文——那些是他必须看的。
  普通会话对审核者同样返回 403，页面上只留一句说明，不显示半截空白。

执行点只有两处，避免判断散落：

1. `InternalAuthInterceptor` 先挡 `viewer` 的一切写操作；
2. 再按 `@RequirePerm` 注解挡"这件事归谁"（`Operator.allows(Perm)` 是唯一的权限矩阵）。

没标注解的写接口会让 `InternalEndpointPermTest` 直接失败；按 `kind` 现场判断的回滚是唯一白名单，
理由写在测试里。这样"加接口忘了改权限表"不会悄悄上线。入库与签字分属两个人，上传的人不能顺手把字也签了。

成员管理走 `/api/internal/members`（只有管理员），后台入口在「运营 → 成员」。
