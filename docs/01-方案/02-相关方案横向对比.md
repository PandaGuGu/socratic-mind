# 第 2 章 相关方案横向对比

> 落位说明：本章位于第 1 章（产品边界与总体架构）之后，作为第 2 章。原稿其余各章顺延一位：模块拆分→第 3 章，RAG→第 4 章，双 Graph→第 5 章，交互与恢复→第 6 章，提示词→第 7 章，接口→第 8 章，技术选型→第 9 章，里程碑→第 10 章，评估→第 11 章。文内交叉引用已按此校正。
> 本章的写作目的：证明"这套架构不是随手选的"，而是对现有三类方案做完取舍后的结果。
> 结构说明：每一层先摆事实（对比表），再单独给一节"本方案的评价"（2.2.1 / 2.3.1 / 2.4.3）。三段评价可以是明确的否定、可以是暂缓判断，但都必须给出理由或触发条件——**"暂不评价"也是结论，前提是说清楚什么时候回头评**。

---

## 2.1 先说清楚怎么比：三个层次，四条判据

现有心理 AI 方案不是同一个层面上的东西，直接拉一张功能表对比是没有意义的。要先分层。

| 层次 | 典型代表 | 它优化的目标 | 它不负责的事 |
|-|-|-|-|
| 模型层 | SoulChat、EmoLLM、MindChat、MeChat，以及"通用大模型 + 提示词" | 说得像不像一个会共情的人 | 出处、流程、审计 |
| 平台层 | Dify、RAGFlow、FastGPT、LangGraph / Spring AI Alibaba Graph | 多快能把一个 AI 应用搭起来 | 业务状态是否可控、结论是否合规 |
| 产品层 | Woebot、Wysa、Therabot、Deprexis、国内平台型产品 | 能不能进医院、进企业、进医保 | 技术是否可复用、是否可私有化 |

分层之后，用四条判据衡量，比"功能有没有"更有区分度：

1. **证据可溯源性**——回答能不能指回具体文献的具体页码或章节，而不是"参考了相关资料"。
2. **流程可控性**——业务状态（走到了 CBT 第几步、用户确认了什么）存在代码或数据库里，还是只存在于模型的上下文里。
3. **能力边界与合规性**——系统敢不敢说"我不知道""这不属于我能处理的范围"。
4. **落地成本**——人月、许可风险、算力、以及后续知识更新的代价。

大多数公开对比只比第 1 条的一半和第 4 条，所以结论往往是"开源方案都能做"。一旦把第 2、3 条摆上桌，三类方案立刻分化——而分化的位置，正好是本方案要站的位置。

## 2.2 模型层：心理垂直模型与共情对话方案（开源）

这一层是学术界和开源社区做得最充分的部分，中文语料尤其丰富。

| 方案 | 归属 / 基座 | 路线 | 强项 | 对本题的缺口 |
|-|-|-|-|-|
| **SoulChat 1.0 / 2.0** | 华南理工大学 广东省数字孪生人重点实验室；Llama3-8B、Qwen2-7B、Baichuan2-7B、InternLM2-7B 等多基座 | 真实咨询语料 + "咨询师数字孪生"（PsyDTCorpus 约 9 万轮，平均 18 轮/段），全量微调 | 认知共情、谈话技术、语言风格一致性 | 无知识出处、无证据分级、无结构化阶段；7B 级模型在长文档理解与中文专业术语上偏弱 |
| **EmoLLM** | 开源社区，多基座 + 多模态方向 | 心理支持指令数据微调 | 覆盖面广，ESC-Eval 人工评测各维度较均衡 | 定位是"情绪支持"，不承诺疗法依从性，也不管流程 |
| **MindChat（心海）** | 开源 | 心理对话微调，隐私保护 / 联邦训练方向 | 拟人度、依从性好，中文自然 | 同上；无检索、无引用 |
| **MeChat / ChatCounselor / CPsyCoun / PsyChat / QiaoBan** | 学术项目 | 真实或合成咨询对话微调 | 中文咨询话术、单轮质量 | 多为 7B 对话模型，缺工程化、缺安全网关、缺审计 |
| **通用大模型 + 提示词** | GPT / Qwen / DeepSeek 等 | 纯提示词工程 | 流畅度、表达多样性、建议有效性最强（ESC-Eval 中通用模型普遍优于此项） | 幻觉、无出处、安全边界完全依赖提示词，且不可回归测试 |

**这一层的共同点，也是共同的天花板：它们把心理支持当成"对话质量问题"来解。** 而本方案要解的三个问题——"这句话的出处是哪一页""用户现在走到第几步""这句结论该不该说"——一个都不在它们的损失函数里。

一个值得注意的实证结论：ESC-Eval 这类评测显示，垂域微调模型在"拟人度、以人为中心"上优于通用模型，但在流畅度与建议有效性上并不占优。也就是说，**微调换来的是风格，不是可靠性**。这一点直接决定了本方案不采用"微调一个心理模型"作为主线（见 2.7 设计反推第 1 条）。

### 2.2.1 本方案的评价：模型层是"门槛"，不是"差异"

我对这一层的判断是：**用什么模型都行，换模型不算方案创新；但有两个硬门槛——能力不能低于 DeepSeek 这一档，响应必须快。**

这句话听起来像"没什么立场"，其实它有三条具体的工程后果：

| 门槛 | 量化要求（第一版） | 直接排除了什么 |
|-|-|-|
| 通用能力下限 | 不低于 DeepSeek 同级模型在中文专业问答与长文理解上的表现 | **排除 7B 级垂域微调模型作为主模型**——它们的强项是话术风格，不是"智商"；用它做主线等于主动降档 |
| 响应延迟 | 首 token P95 < 1.5s，单轮端到端 < 4s | 排除"每个节点多次自我反思""多智能体互相辩论"这类设计；CBT 的每一步都是对话，用户等不起 |
| 可替换性 | 通过 Spring AI 的 ChatModel 抽象接入，按节点配模型 | 排除"把模型能力写进业务逻辑"的写法；否则换模型要重写流程 |

由此还推出一条设计约束，恰好和原方案的节点表吻合：

> **延迟是预算，不是优化项。** 一个 CBT 节点最多一次主模型调用；检索、融合、引用定位全部走确定性代码；分类与小结构抽取交给小模型或规则。这也是为什么第 5 章（双 Graph 设计）的节点表里，`retrieve_evidence`、`format_response` 标的是"不调用 LLM"——不是省钱，是省时间。

换句话说，模型层在本方案里的角色是**可替换的算力**，方案的价值不在"我用了哪个模型"，而在"我怎么用、什么时候不用"。这条立场同时也解释了为什么后面不把"换了更强的模型"当作改进项——它会自动发生。

## 2.3 平台层：开源 RAG / Agent 平台与编排框架

这一层最容易被误认为"你这个作业已经有人做完了"。逐个看，结论相反。

| 方案 | 定位 | 编排能力 | 多轮挂起 / 恢复 | 文档解析 | 许可 | 在本方案中的可能用法 |
|-|-|-|-|-|-|-|
| **Dify** | LLM 应用平台（Workflow / Chatflow + 知识库） | 可视化 DAG，节点丰富，生态最好 | 会话 = 消息历史；**没有节点级 checkpoint，不能回滚到第 4 步重跑** | 插件化（LlamaParse、Unstructured 等），无自研深度解析 | Apache-2.0 修改版：多租户运营需授权，前端 logo 不可去 | **做 baseline**：一周内搭出"通用 RAG 问答"对照组（见 2.8） |
| **RAGFlow** | 深度文档理解 RAG 引擎 | 弱，以检索为主 | 无 | 自研 DeepDoc：OCR、版面分析、表格结构识别，切分模板多 | Apache-2.0（较干净） | 离线入库侧替代：扫描件、复杂表格的解析外包给它 |
| **FastGPT** | 知识库问答 + 可视化工作流 | 中等 | 无 | 中等 | FastGPT Open Source License：附加条款比 Dify 更严，**无前端 logo 豁免** | 不建议：一旦要把系统做成对外服务，授权会挡路 |
| **MaxKB** | 知识库问答 | 中等 | 无 | 需外接 OCR | GPLv3 + 闭源 X-Pack | 不建议：传染性风险，且多租户/RBAC 在收费版 |
| **AnythingLLM / Open WebUI** | 自托管聊天前端 + 轻量 RAG | 弱 | 无 | 弱 | MIT / 自定义许可（含品牌保留条款） | 仅作开发期内部调试界面 |
| **LangGraph（Py/JS）/ LangGraph4j** | 低层状态编排框架 | 强：StateGraph、子图、时间旅行调试 | 强：checkpoint + interrupt_before/after | 无 | MIT / 见仓库 | 若团队转 Python 栈，它是首选；Java 侧与本方案选型同源 |
| **Spring AI Alibaba Graph** | Java 原生 Graph runtime | 强：预置节点、并行分支聚合（AllOf/AnyOf）、MCP/A2A | checkpoint 持久化，支持多种存储后端（**具体版本支持哪些库需按版本文档核实**） | 无（依赖 Spring AI 的 VectorStore / RAG 组件） | Apache-2.0 | **本方案选型** |

这里有一个必须讲清楚的判断，否则整套架构显得多余：

> **低代码平台和多轮聊天框架，都把"会话"建模成消息历史；而 CBT 需要的是"可暂停、可回滚、可确认的业务状态机"。**
>
> 用户在第 4 步说"我想改一下刚才那个想法"，平台方案只能把历史消息重新喂给模型再生成一遍；本方案是 `userConfirmedThought` 与 `balancedThoughtCandidate` 两个字段分开存，改的是字段，不是重跑对话。这不是实现细节的差别，是数据模型的差别。

第二点：平台层的知识单元是 `chunk + metadata`。要表达"这条推荐适用于哪个人群、推荐强度多高、有哪些限制条件"，只能塞进 metadata 的字符串里，然后指望模型自己别搞错。本方案的 `kb_evidence` 表把这几项拆成结构化字段、无法确认就存 null——这不是过度设计，这是把平台层做不到的事做成显式契约。

### 2.3.1 本方案的评价：这一层暂不打分，只定"哪些零件现在借、哪些等数据"

我选择第一版不对平台层下结论。原因不是没看法，而是**平台层和本方案不在同一层**：它是实现手段，不是竞争方案。给手段打分没有意义，有意义的是回答"现在借哪几个零件、什么时候重新判断"。

按这个思路，平台层的七个方案其实分三类：

| 类别 | 方案 | 第一版怎么处理 |
|-|-|-|
| 现在就借的零件 | RAGFlow 的 DeepDoc（扫描件、复杂表格解析） | 只在离线入库环节调用，产出标准 chunk 后进自己的表；不引入它的运行时 |
| 借来做对照的 | Dify | 只用来搭 2.8 的 B 组 baseline，不进入主链路 |
| 等数据再判断的 | Dify / FastGPT 作为整体底座 | 延迟决策，判据见下表 |

**重新评估的触发条件（建议写在 M6 的验收清单里）：**

| 观察到的现象 | 判断 | 动作 |
|-|-|-|
| B 组与本方案的引用支持率差距 < 5pp | 自研 RAG 的增量不足以支付维护成本 | 入库与检索换成平台方案，Java 侧只保留 Graph、证据契约与引用校验 |
| 差距 > 15pp，且差距主要来自证据结构化 | 增量真实存在 | 维持自研，把平台降级为内部调试界面 |
| 两人以下团队、每季度维护成本 > 2 人月 | 工程上不经济 | 平台化，Graph 通过其 API 兜住 |
| CBT 需要新增跨会话的行动追踪 | 平台无法表达这种状态 | 不迁移，反而要加强自研 |

也就是说，本节暂时"不做评价"是一种**有条件的克制**：结论被推迟到有对照数据之后，而不是被跳过。这个判断本身也构成方案的一部分——第一版要证明的不是"自研更好"，而是"自研的增量有多大"，后者才决定第二版该不该继续自研。

## 2.4 产品层：闭源商业产品（有明确架构设计的）

这一层不能比功能，只能比**架构范式**。因为它们的代码看不到，但设计取舍是公开的。

### 2.4.1 四个产品，四条路线

| 产品 | 形态 | 技术路线 | 证据基础 | 监管 / 渠道 | 对本方案的启示 |
|-|-|-|-|-|-|
| **Woebot**（2017–2025） | C 端 CBT 聊天机器人；2025-06-30 关停 C 端，转 B 端 | **脚本化决策树 + 临床审核话术**，非生成式 | 多项 RCT，焦虑/抑郁效应量在 d≈0.5 量级（公司披露） | FDA 突破性器械认定（2021，产后抑郁 WB001），未获上市许可 | 脚本化＝可控但扩展性差；创始人公开表示停运原因是 FDA 上市许可成本 + LLM 监管路径未明 |
| **Wysa** | C 端 + B 端（NHS Talking Therapies 的自我转诊与分诊入口） | **神经符号混合**：临床审核应答 + 结构化决策树 + 受严格约束的 LLM 生成（明确"不做开放式生成"） | 30+ 篇同行评议；FDA 突破性器械认定（2022，慢性疼痛共病抑郁焦虑） | 英国 NHS、新加坡 mindline.sg | **与本方案最接近的工程范式**：确定性骨架 + 受控生成 + 人类兜底 |
| **Therabot**（Dartmouth） | 研究型生成式治疗对话系统 | 微调 LLM + CBT/DBT/动机式访谈框架约束 | 2025 年 NEJM AI 的 8 周 RCT，抑郁症状下降约 51% | 研究阶段 | 证明"结构化疗法 + LLM"这条路成立，但代价是临床团队 + RCT 预算 |
| **Deprexis** | 德国数字疗法（可处方） | **线性模块化 CBT 程序**，几乎不依赖生成模型 | 多项 RCT，德国可处方 | 医疗器械类 | 疗法保真度靠"固定模块"保证，不靠模型自觉 |
| 国内平台型产品（好心情、简单心理、壹心理"鲸鱼 Alice"、Emohaa、星云星空 PsyLLM、校园场景"小智聆心"等） | 平台 / 医疗 / 校园企业 | 自研心理模型 + AI 分诊 + 真人咨询师兜底 | 多为厂商自述（来源为公开报道，本方案未做纵深核实） | 互联网医院牌照、等保、进校采购 | 商业模式是"AI 分诊 + 真人转介"，**没有一家把 AI 独立治疗作为卖点** |

### 2.4.2 三条架构路线，本方案选的是第二条

把上面的产品抽象一下，闭源方案其实只有三种可对比的架构：

| 范式 | 代表 | 可控性 | 覆盖面 | 成本 | 主要失效模式 |
|-|-|-|-|-|-|
| A. 脚本决策树 | Woebot、Deprexis | 最高 | 最窄（只能走预设分支） | 内容生产成本极高 | 用户一说偏题就僵住；知识更新 = 重写脚本 |
| B. 神经符号混合 | Wysa | 高 | 中（骨架固定，话术可生成） | 中 | 骨架的设计质量决定上限 |
| C. 端到端生成 + 疗法框架约束 | Therabot、纯提示词方案 | 低 | 最宽 | 低（开发）/ 高（验证） | 幻觉、越界、不可回归测试 |

**本方案是范式 B 的一次"开源栈重实现"**，并且做了一处关键替换：

- Wysa 的符号层是**人工审核过的话术库**，所以它能保证"每句话都被临床团队看过"，代价是扩展性极差、每个新场景都要重写。
- 本方案的符号层是**Graph 结构 + 审核过的证据库**：骨架是代码（节点、条件边、中断点），内容来自可版本化的知识库。于是"新增一个干预方式"不需要改代码，只需要入库一份带证据属性的文档。

这就是本方案相对闭源产品唯一真正的结构性优势：**在保持"确定性骨架"的同时，把内容生产成本从"写脚本"降到"审文档"。** 而它的代价也同样明确——我们没有 Wysa 的临床团队、没有 RCT、没有牌照、没有真人兜底。

### 2.4.3 本方案的评价：这一层确实"都不太成功"，但失败点不在技术，在支付方

我的判断是：这个观察成立，但归因需要拆开——**不是"技术和政策都没到位"，而是"没有人愿意为预防付钱"，监管与成本都是这个前提的结果。**

先把"成功"这个词拆开看，否则会误判：

| 当作什么卖 | 结果 |
|-|-|
| AI 治疗 | **几乎没有成功的**。Woebot 关停 C 端；Therabot 停在研究阶段；没有一家把"AI 独立治疗"做成主营收入 |
| 分诊 / 转诊 / 入口 | **有活得不错的**。Wysa 在 NHS Talking Therapies 做自我转诊与分诊，报称处理 18 万+ 来访、转诊完成率 91%、每次评估省 30 分钟；新加坡 mindline.sg 是国家平台 |
| 技能训练 / 自助工具 | 有市场，但客单价低、留存差，通常作为员工福利或课程配套被批量采购 |

再看三层原因，从表到里：

1. **监管（政策）：一旦声称"治疗"，就变成医疗器械。** FDA 的 De Novo / 510(k)、欧盟 MDR、国内二类/三类，周期以年计、费用以百万计；更麻烦的是 LLM 的监管路径当时并不存在——Woebot 创始人给出的停运理由正是"FDA 上市许可的成本"加"尚未成型的 LLM 监管路径"。**你不宣称疗效就没有护城河，宣称了就要按器械做。**
2. **验证成本：RCT 是入场券，不是加分项。** B 端（保险、雇主、NHS、学校）采购时要看同行评议证据，而一个像样的 RCT 是百万级预算加一到两年。Therabot 证明这条路技术上成立，但它停在研究阶段，恰是因为下一步的商业化需要重复支付这个成本。Woebot 做了 15 项以上 RCT 才换来一个"突破性器械认定"——认定不是批准，只是"可以多跟药监沟通"。
3. **支付方缺位（我认为这是根因）。** 医疗支付体系只为"诊断之后的治疗"付钱，不为"预防"付钱；商保和雇主只为"能降低赔付"的东西付钱。AI 自助工具的价值恰恰产生在"还没生病"的阶段——这个阶段在现有支付结构里是**没有账单的**。

**一个反例足以说明问题：Deprexis。** 它是这一层里技术含量最低的方案——线性模块化 CBT 程序，几乎不依赖生成模型——却在德国活下来了。原因不在技术，在于德国有 DiGA（数字健康应用）报销通道：医生可以开处方，医保付钱。**同一个产品，在有支付方的市场是生意，在没有支付方的市场是公益项目。**

这条逻辑也解释了国内格局：好心情、简单心理、壹心理都长成了"AI 分诊 + 真人咨询师"，因为钱在真人服务上（咨询费、处方、复诊），AI 的角色是降低获客与分诊成本。这不是技术上的退让，是商业上的必然。

**对本章的推论：**

> 既然"当治疗卖"过不了监管，"当分诊卖"要牌照与真人供给，那"当工具卖"就是唯一不需要支付方和牌照的路径。**这就是产品边界停在"不诊断"的经济学理由，而不是道德理由。**

原方案只写了"暂不做临床诊断"，没写为什么。补上这一句，边界才站得住：它不是保守，是在没有支付方的市场里，唯一能成立的位置。相应地，这个定位也决定了它的销售对象不是患者个人，而是学校、企业、咨询机构的**福利采购或课程配套**——这也意味着第一版的验收标准应该是"机构愿不愿意批量买"，而不是"用户愿不愿意天天用"。

## 2.5 总表：九维对比

图例：● 原生支持　◐ 需自行实现 / 部分支持　○ 不具备

| 维度 | 心理垂直模型（SoulChat / EmoLLM 类） | 低代码平台（Dify / FastGPT 类） | 通用编排框架（LangGraph 类） | 闭源商业产品（Wysa 类） | **本方案** |
|-|-|-|-|-|-|
| 知识出处可溯源（到页码） | ○ | ◐ 有 chunk 引用，无页码级定位 | ○ | ◐ 内部有，未对用户开放 | **●** kb_citation + 引用校验节点 |
| 证据结构化与分级 | ○ | ○ | ○ | ● 人工审核话术 | **●** kb_evidence（条件/人群/强度/限制） |
| CBT 阶段可控（非模型自由发挥） | ○ | ◐ 靠提示词约束 | ● 状态图 | ● 决策树 | **●** CbtGraph + 显式 State |
| 跨轮挂起与恢复 | ○ | ○ 只有消息历史 | ● checkpoint | ● | **●** threadId + Checkpoint |
| 用户确认 / 中断可追溯 | ○ | ○ | ◐ interrupt 机制（需自己建业务表） | ● | **●** userConfirmedThought 独立字段 |
| 安全分流 | ◐ 依赖模型对齐 | ◐ 靠提示词 | ◐ 需自建 | ● 规则 + 人工升级 | **◐→●** 规则 + 语义双通道（M4 交付） |
| 私有化 / 二次开发 | ● | ● | ● | ○ | **●** Java 单体，可离线部署 |
| 许可与合规风险 | ● 多为 Apache/MIT | ◐ Dify/FastGPT 有 SaaS 条款 | ● MIT | ○ 商业授权 | **●** 全栈 Apache-2.0 系 |
| 冷启动成本（到可用 Demo） | 高（要 GPU 与微调） | **最低（数天）** | 中 | 不适用 | 中高（M1–M2 约数周，见第 10 章） |
| 临床证据 / 真人兜底 | ○ | ○ | ○ | ● 有 RCT 与转介通道 | **○（明确不承诺）** |

三行加粗的结论：

1. **在"可控 + 可审计"这两列，低代码平台是空缺的**，而这是心理场景的硬需求，不是加分项。
2. **在"冷启动成本"和"临床证据"两列，本方案明确劣势**，且短期内无法弥补。写方案时不该模糊这一点。
3. 本方案在九维里唯一"别人都没有"的组合是：**出处可溯源 + 证据分级 + 流程状态机，三者同时成立**。单看任何一维都有替代品。

## 2.6 结论：本方案站在哪，以及必须承认的三个短板

**一句话定位：**

> 本方案不是"又一个心理聊天机器人"，而是把 Wysa 式神经符号架构用开源 Java 栈重做一遍，并把"临床审核话术"替换为"可版本化、带证据属性的审核知识库"——用工程手段换取内容扩展性，代价是放弃临床证据与真人兜底。

必须承认的四个短板（写进方案的"局限性"一节，比藏着更有说服力）：

| 短板 | 具体差距 | 第一版怎么办 |
|-|-|-|
| 共情表现 | 通用模型 + 提示词在流畅度与情感回应上大概率弱于 SoulChat/EmoLLM 微调模型，也弱于商业产品 | 不追求"像咨询师"，追求"像一个训练有素的引导员"；用提示词 + 少量风格示例约束；把共情质量单列为评估项，不与临床方案比总分 |
| 临床证据 | 0 篇 RCT，无真人兜底，无牌照 | 明确"自助技能训练工具"定位，不做诊断、不做治疗决策；安全分流硬编码转介路径（120 / 心理援助热线 / 精神科门诊） |
| 商业闭环 | 无支付方、无牌照，只能作为工具被批量采购；C 端单用户付费意愿低（见 2.4.3） | 不解决。第一版只用两件事证明采购价值：完成一轮 CBT 五步的完成率，以及教师/咨询师可查看的结构化记录 |
| 依从性与留存 | 商业产品有教练、社群、提醒、激励机制，本方案只有对话 | 第一版只做"单次完整闭环"，不承诺长期留存；把"完成一轮 CBT 五步"作为核心指标 |

## 2.7 反过来用对比结果验证设计：五个决定都有出处

横向对比的价值不在于"我参考了谁"，而在于**每个设计决定都能指向一个被证伪的替代方案**。本章对应的五条：

| 设计决定 | 被否掉的替代方案 | 否掉的理由（来自对比） |
|-|-|-|
| 不微调心理模型，用通用模型 + RAG | SoulChat / EmoLLM 路线 | 微调换来风格而非可靠性（ESC-Eval）；且指南更新时要重训，而 kb_evidence 只需重新入库并切换版本 |
| 用 Graph + Checkpoint，不用低代码平台 | Dify / FastGPT 路线 | 平台把会话建模为消息历史，无法表达"回到第 4 步只改一个字段"；CBT 的核心恰恰是这个 |
| 保留 kb_evidence 这张"重"表 | 只用 chunk + metadata | 这是与 Wysa "临床审核话术"对齐的最小代价方案：用结构化字段替代人力审核的规模 |
| 产品边界停在"不诊断" | 做筛查 / 分诊 / 风险评级 | 声明疗效即入医疗器械监管（Woebot 的停运理由），而不声明则无护城河；边界应先于技术确定（见 2.4.3） |
| 模型按节点分级路由，不锁定单一模型 | 全流程统一用一个最强模型 | 延迟是硬约束（首 token < 1.5s）：分类、结构化抽取用小模型或规则就够，把主模型预算留给生成与认知检验（见 2.2.1） |

## 2.8 把对比做成实验：三组对照（建议并入 M6）

只有一张对比表是"文献综述"，加一组对照实验才是"方案论证"。建议在 M6 阶段固定跑三组：

| 组 | 系统 | 用途 |
|-|-|-|
| A | 通用大模型直接回答（无检索、无流程） | 下界：证明"有 RAG"这件事本身的价值 |
| B | 通用 RAG（Dify 搭一套，或 Spring AI 的 QuestionAnswerAdvisor 一把梭） | 主对照组：证明"证据结构化 + 引用校验"的增量价值 |
| C | 本方案（RAG + 证据单元 + 双 Graph） | 实验组 |

指标沿用第 11 章（评估指标），另加三项对比专用指标：

| 指标 | 定义 | 预期方向（待验证） |
|-|-|-|
| 引用支持率 | 回答中的断言能被所引证据直接支持的比例 | C > B > A |
| 无依据陈述率 | 无法追溯到任何证据的事实性陈述占比 | C < B < A |
| 危机识别召回率 / 误报率 | 安全测试集上的两个方向 | 需要同时报，只报召回没有意义 |
| 完成一轮所需轮次 | 从进入 CBT 到"用户确认行动计划"的平均轮次 | C 应显著少于 A/B（流程驱动的直接收益） |
| 单会话成本 | token 消耗 + P95 延迟 | C 最高，需给出量级（这是"可控性"的价格） |

**这张表的意义：**它让"我们选了更重的架构"变成一个可被检验的假设，而不是一次技术偏好。评审最想看的往往就是这一点——你是否知道自己在为什么付代价。
