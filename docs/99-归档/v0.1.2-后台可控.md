# v0.1.2 后台可控性

这一版回答三个问题：安全分流、限流数值、话术，能不能由运维在后台改。
结论：**都能改，但"改坏"会被服务端拒绝**；每次生效都有版本快照，可回滚。

## 一、现在能在后台改什么

页面：`/internal/settings.html`（"规则与参数"），与画布、输出策略并列。

| 对象 | 改什么 | 生效方式 | 门禁 |
|-|-|-|-|
| 安全规则 | 新建 / 删除 / 改 id、名称、级别（hold·context·signal·ignore）、正则、启停 | 保存即热加载，下一轮对话生效 | 结构校验 + 用例回放；至少 1 条启用的 hold 规则 |
| 发布用例 | 新建 / 删除 / 改用例文本、期望（HOLD·NOT_HOLD·NOT_PASS·PASS）、说明 | 与规则同一次保存 | 下限：≥5 条 HOLD、≥2 条 PASS，不能删空 |
| 运行参数 | 单条消息上限、每分钟消息数、每小时开新会话数 | 保存即热加载，下一次请求生效 | 范围校验（100–20000 / 1–1000 / 1–10000） |
| 系统话术 | 6 句非阶段话术：结束后再说话、待确认拦截、确认回执、主动结束、平衡模板、总结模板 | 保存即发布，与画布共用流程版本 | 键白名单 + 每键占位符白名单 + 800 字上限 |
| 阶段提问 | 11 个节点的话术、分支、模型档位 | 画布，原有能力 | 原 `FlowValidator` |
| 历史与回滚 | flow / safety / limits 三份配置的历史版本；列表带时间与操作者 | 点「看」查看该版本内容并与当前逐项对比（差异行高亮），可从对比面板回滚 | 回滚内容同样过门禁 |

接口：

```
GET  /api/internal/safety/rules           当前规则 + 路径 + 历史版本
PUT  /api/internal/safety/rules           保存（不可用则 422，附前三条失败原因）
POST /api/internal/safety/rules/validate  只校验草稿，不落盘，返回逐条错误
POST /api/internal/safety/rules/test      贴一句话，看当前规则怎么判
GET  /api/internal/safety/cases           当前用例表（随 GET rules 一起返回）
GET  /api/internal/limits                 当前参数
PUT  /api/internal/limits                 保存
GET  /api/internal/config/history         flow / safety / limits 的版本列表
POST /api/internal/config/rollback        回滚到指定版本（作为新版本生效）
```

操作者：请求头 `X-Internal-Actor`，缺省 `ops`，写进版本记录。

## 二、门禁是怎么拦的

安全规则的用例表也由运维维护（`config/safety-rules.json` 的 `cases`），保存时逐条回放：

- 11 条必须 HOLD：`我真的不想活了`、`我想死`、`我想割腕`、`I want to die`、`我妈不想活了，我也不想活了`……
- 3 条不许 PASS：指向他人、引用语境的句子必须至少进复核；
- 4 条必须 PASS：`累死了`、`笑死我了`、`想死你了`、`他把我气死了`。

保存时若结果与期望不符，拒绝并指出是哪条用例：

```
用例「我真的不想活了」应暂停并转介，当前结果是放过（最直接的自伤表达）；…；等共 11 条
```

"加词"不受限制：给 `self_harm` 追加 `|不想撑了` 可以保存，且立即对下一句话生效。
"加规则"同样不受限制：新建一条 `local_slang`（`想一了百了|撑不住了想走`）保存即生效；
"删规则"也可以——但如果删掉的是唯一覆盖某条用例的规则，回放会指出失效用例，而不是靠写死的 id 拦住。

- `SettingsApiTest`（7）：无令牌 401、改窄 422、加词 200、新增/删除规则、用例可加不可清空、参数 0 被拒、历史与回滚可用。

### 手工端到端（H2 档，2026-11-19）

```
GET  /api/internal/safety/rules        → v1，6 条（hold×2 / context×2 / signal / ignore）
PUT  把 self_harm 改窄成 "只有这句话才算|zzz"
                                       → 422，列出 11 条失效用例
PUT  self_harm 追加 "|不想撑了"        → 200，v2
POST /safety/rules/test {"我真的不想撑了"} → hold=true，rule=self_harm
POST /safety/rules/test {"累死了"}      → hold=false，review=false
PUT  /limits {maxMessageChars:100,…}   → 200，v2
POST 发送 150 字消息                    → 422「单条消息不能超过 100 字」
PUT  /flow 改 confirm_ack 为「【E2E】已记录：…」
                                       → v9，下一轮确认回执立即变成该文案
POST /config/rollback {flow, 9}        → 生成 v11，回执回到 v9 的版本
GET  /config/history                   → flow [11,10,9] / safety [2] / limits [2]
```

## 四、边界

1. **下限在代码里**：内容（规则、用例）全可改，但"至少一条 hold 规则、至少 5 条 HOLD 用例、至少 2 条 PASS 用例"是常量。要连下限一起放开，等于允许把安全分流关掉。
2. **改宽不设上限**：多加词只会让误报上升，代码不做价值判断；需要靠复核实测。
3. **限流是单机的**：多实例部署仍需网关层限流。
4. **没有角色**：任何持内部令牌的人都能改；审计只到"操作者名字"这一层（客户端自报）。
5. **安全规则仍未经临床审核**：可编辑性提高了响应速度，但没有改变"规则表来自工程常识"这个事实。
