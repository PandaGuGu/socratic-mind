# 文档规范

适用于 `docs/` 下所有文件。

## 1. 文件头

```yaml
---
title: 数据模型
status: 定稿        # 定稿 | 草案 | 待决策
updated: YYYY-MM-DD
---
```

`status` 不是装饰：`草案` 的内容不能被当作开发依据引用。

## 2. 命名与位置

| 内容 | 放哪 | 不放哪 |
|-|-|-|
| 产品定位、边界、方案对比 | `01-概览/` | 实现细节 |
| 模块、流程、契约、数据模型 | `02-架构/` | 某一版改了什么 |
| 状态机、安全、后台、界面、提示词 | `03-设计/` | 还没定的想法（先写 ADR 或待决项） |
| 一个决定一篇 | `04-adr/` | 操作步骤、验证过程 |
| 约束：文档、UI、外部依赖 | `05-规范/` | 具体实现说明 |
| 版本、指标、对标、需求对齐 | `06-评估/` | 过程流水账 |
| 截图 | `assets/current/` | 根目录、中文文件名 |

文件名即标题，短、具体、不含版本号。文件一旦被外部引用就不要再改名；
确需改名时，在同一提交里改完全部引用。

## 3. 交叉引用

| 场景 | 写法 |
|-|-|
| 其它文档 | `[数据模型](../02-架构/04-数据模型.md)` |
| 同文档小节 | `[§2 组件](#2-组件)` |
| 代码位置 | 直接写路径与类名，如 `CbtFlow.advance` |

禁止"上一章""前面提到过"——文档会被单独转发，这些词在单篇里没有指向。

## 4. 表格与图

- 一张表只回答一个问题；对比表必须有"结论"或"本方案"一列。
- 单元格不写长段落，超过两句改成小节。
- 图优先 mermaid 写在正文里，保证可 diff；截图、导出件才进 `assets/`。
- 架构图必须与正文表格一致；改图要同步改表。

## 5. 语言

- 中文正文；术语首次出现给英文原词，如"证据单元（evidence）"。
- 不用营销词（"革命性""颠覆"），不写无法验证的形容词。
- 结论句放段首，理由跟在后面。评审读的是第一句。
- 数字必须带测量条件：不是"很快"，而是"P95 30 秒，CPU，34 条样本"。

## 6. 一致性

**同一个事实只允许有一个当前版本。**

发现两处描述同一件事：保留被更多文档引用的那份，另一份删掉或改成链接。
文档与代码冲突时以文档为准，并在同一提交里改代码或改文档——不能两边都对。

## 7. 变更

| 改动 | 必做 |
|-|-|
| 改结论 | 新增 ADR 或更新对应 ADR，并在正文挂链接 |
| 改数字 | 注明来源与测量条件 |
| 新增/移动文档 | 更新 [docs/README](../README.md) 与根 README 的阅读路径 |
| 删除内容 | 直接删，靠 git 历史追溯；不要让两份互相矛盾的真值并存 |

最后一条与常见做法相反：本项目不留 `99-归档`。设计文档一旦不成立就删掉，
历史在 `git log -- docs/` 里。归档目录会让人误以为旧结论还有效。

改完文档跑一次：

```bash
python scripts/check-links.py
```
