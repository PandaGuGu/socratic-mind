# ADR-0006：保留 kb_evidence 这张"重"表

- **状态**：已接受
- **日期**：2026-11-17
- **相关**：[§4.2](../01-方案/04-RAG知识数据架构.md)、[§2.3](../01-方案/02-相关方案横向对比.md)、[§2.7](../01-方案/02-相关方案横向对比.md)

## 背景

主流做法是 `chunk + metadata`：把"适用人群""推荐强度""限制条件"塞进 metadata 的字符串，让模型自己别搞错。加一张 `kb_evidence` 表意味着入库要人工补字段，成本真实存在。

## 决策

保留 `kb_evidence`，把证据属性拆成**结构化字段**（condition / population / intervention / recommendation_strength / evidence_quality / limitations / review_status）。**无法确认的字段存 `null` 或 `unknown`，禁止让模型补全。**

## 备选方案与被否原因

| 方案 | 为什么没选 |
|-|-|
| 只用 chunk + metadata | 无法表达"这条推荐不适用于某人群"；模型面对字符串 metadata 会自行归纳，一旦归纳错就是错误建议 |
| 让 LLM 入库时自动抽取证据字段 | 会编造推荐强度与证据质量——这恰好是本项目最不能容忍的错误类型 |
| 全部人工标注，不做结构化表 | 无结构可查，等于回到"话术库"路线，扩展性丧失 |

## 后果

**好处：** 引用可以精确到"哪条推荐、对谁、强度多少、有何限制"；这是与 Wysa"临床审核话术"对齐的最小代价方案；也是 [§2.3.1](../01-方案/02-相关方案横向对比.md) 对照实验里 C 组相对 B 组的核心增量。

**代价：** 入库是**人工瓶颈**，每份文档都要审核补字段；字段设计要经得起真实指南文本考验（待办：与 1–2 份真实指南对齐一轮）。

**复查触发条件：** 若对照实验显示 B 组与本方案引用支持率差距 < 5pp，说明该表的增量不足以支付维护成本，届时考虑降级 metadata + 平台化（判据见 [§2.3.1](../01-方案/02-相关方案横向对比.md)）。

## 备注

**待核实**：`evidence_type` 的取值枚举。先按真实指南各取 20 条试标，枚举稳定后再写 DDL 约束，避免过早固化。
