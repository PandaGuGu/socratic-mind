# ADR-0008：安全规则、运行参数与系统话术都进后台，但"可编辑"有门禁

- **状态**：已接受
- **日期**：2026-11-19
- **相关**：[安全分流规则](../02-设计/安全分流规则.md)、[内部后台](../02-设计/内部后台.md)、[ADR-0007](ADR-0007-会话归属与内部接口鉴权.md)

## 背景

v0.1.1 之后，用户问了一个很实际的问题：安全分流、限流数值、话术，运维能不能自己改？

当时的答案是"一半能"：

- 话术：画布能改 10 个节点，但 `CbtFlow` 里还写死 6 句用户可见的话（结束语、确认回执、平衡/总结模板）；
- 安全规则：6 个正则全是 Java 常量，后台只能改 `SAFETY_HOLD` 那段话术；
- 限流与长度：`2000 字 / 60 条每分钟 / 30 次每小时` 都是常量，改一个数字要重新打包。

这三件事的共同点是：它们都是"半夜会想改、改错会出事"的东西。只给"改代码"这一条路，等于让值班的人要么忍着，要么绕过流程。

## 决策

**1. 三样东西都进后台，各自有发布门禁。**

| 对象 | 配置文件 | 门禁 |
|-|-|-|
| 安全规则 | `config/safety-rules.json` | 结构校验 + 可编辑的用例表回放；至少一条启用的 hold 规则；用例表下限（5 条 HOLD / 2 条 PASS） |
| 运行参数 | `config/limits.json` | 范围校验（例如每分钟 1–1000） |
| 系统话术 | `config/flow-params.json` 的 `messages` | 键白名单 + 每个键的占位符白名单 + 长度上限 |

规则内容与用例内容都由运维维护：可以新建一条规则、删掉一条不再适用的规则、把某句话加进/移出用例表。
代码里只剩**下限**：至少要有一条启用的 hold 规则，用例表至少保留 5 条"必须暂停"和 2 条"必须放过"。

想让"不想活"不再触发暂停，可以删规则，但用例表会立刻指出失效的那几条；想把用例一起删空，
下限会拦住。这是"可编辑"与"可放水"之间的分界——不靠写死 id，靠行为基线。

**2. 每次生效都是一个新版本，历史只追加。**

保存时写入 `config/history/<kind>/v<n>.json`。回滚不是覆盖旧文件，而是"把旧快照当成一次新的保存"，
版本号继续往前走——这样每一次生效都能查到当时是什么内容、谁改的（`X-Internal-Actor`）。

## 备选方案与被否原因

| 方案 | 为什么没选 |
|-|-|
| 安全规则继续只留在代码里 | 安全上最省事，但运维改一个变体就要发版；实际结果是没人改，规则表越来越旧 |
| 规则放进数据库、加审核流 | v0.1 没有账号与角色，做不出"审核人"；文件 + 令牌 + 回放校验已经能覆盖当前规模 |
| 允许关闭整个安全分流 | 这等于给了一个"关掉刹车"的开关；只允许改词表与语境规则，不允许移除 HOLD 通道 |
| 只做版本号不做回滚 | 改了坏规则时只能翻 git；值班的人通常没有那个权限和时间 |

## 后果

- 后台多一个页面（`/internal/settings.html`）：改规则、改数值、改系统话术、看历史、回滚；
- 规则"改窄"会被用例表拦住，但**改宽不受限制**——加太多词会让误报上升，这需要人工判断，代码不做价值判断；
- 用例表可以改、可以加，但不能删空或降到下限以下：底线由"行为"定义，而不是由某几条写死的规则 id 定义；
- 配置文件损坏时继续使用上一版并打 ERROR 日志，不会静默退化成"无规则"；
- `config/history/` 是本机运行状态，已加入 `.gitignore`；配置本身仍进库、仍可 review。
